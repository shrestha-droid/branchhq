The Change Proof format

One statement about one change to a codebase, normally a pull request: what changed, what was checked, and what the checks found, whoever or whatever wrote the code. Anyone can check one without Branch HQ: it needs SHA-256, Ed25519, an RFC 3161 timestamp check and git.

What it says, and what it does not

A proof does not say a change is correct or safe. It says which checks ran on exactly this change and what they found, in a form that cannot be edited afterwards without it showing. Free to implement: write proofs or checkers in any tool.

The file

{
  "proof":  { ...the statement... },
  "sha256": "hex SHA-256 of the canonical statement",
  "sig":    { "key": "fingerprint", "value": "base64 Ed25519 signature" },
  "stamp":  { "tsa": "...", "genTime": "...", "headHash": "<sha256>", "recordCount": 1, "tsr": "base64 RFC 3161 response" }
}

sig and stamp are optional. A proof made where no key is available, such as a pull request from a fork, is only timestamped.

The statement

format"branchhq-change-proof/1"
createdAtISO time the statement was made
toolwhat made it, with its version
repositoryname, and remote (the origin URL, or null)
changebaseRef (as given, e.g. origin/main), base (the merge-base commit), head (commit), files, linesAdded, linesRemoved
change.files[]path; status (git's letter: A added, M changed, D deleted, T type changed); oldBlob, newBlob (git blob ids, null where the file did not exist); added, removed (lines)
commits[]each non-merge commit in base..head: sha, author ("Name <email>"), date, subject, ai (AI tools the commit names)
aievery AI tool named across the commits
testsstatus (passed, failed, already-failing, no-tests, could-not-run, not-run) and command
breakstried, caught, missed[] (file, line, before, after), notTried (why none or fewer were tried, or null)
findingscomparedWith (commit), new[] (severity high, medium or low, title, where), alreadyThere (findings the base also had)
personalDatanewFields, newRecipients, newGaps, closedGaps (India's DPDP Act), or null when the code holds no personal data
recordlastEntry: the hash of the last entry in the project's evidence record when the proof was made, or null
verdictthe statement in plain English

Terms

  • AI named in the commits: the commit's author, or a Co-authored-by: line, names a known AI tool (Claude, GitHub Copilot, Cursor, OpenAI Codex, ChatGPT, Gemini, Devin, Aider, Windsurf, Amazon Q). Code written with AI and not labelled cannot be seen.
  • A deliberate break is one small edit to one line the change added: a comparison flipped (>= to <), && made ||, return true made return false, + made -. Each is applied alone and the project's tests are run; it is caught when the tests then fail. Breaks are tried only when the tests pass on the change as it is. Catching them shows the tests check what those lines do; it does not show the code is free of faults.
  • New findings are those the head has and the base does not, place by place. A place is the same when the finding's title (numbers ignored), its file and its line of code match, so code that only moved is not new.

Checking a proof

  1. The hash. Serialise proof canonically: object keys sorted by code point at every level, keys with no value left out, no whitespace, strings and numbers as JSON.stringify writes them. The SHA-256 of those UTF-8 bytes, in lowercase hex, must equal sha256.
  2. The signature. The project keeps its Ed25519 public key in its repository at .branchhq/signing-key.pub (PEM, SPKI). Its fingerprint is the first 16 hex characters of the SHA-256 of the key's DER bytes. sig.key must equal that fingerprint, and sig.value must be a valid signature, by that key, of the ASCII bytes of the sha256 hex string. Get the fingerprint from the project once, by a route other than the repository: someone who can push could replace both the key and the signatures.
  3. The timestamp. stamp.headHash must equal sha256. stamp.tsr is an RFC 3161 response from stamp.tsa whose message imprint is the 32 bytes of sha256 itself: 
    openssl ts -verify -digest <sha256> -in token.tsr -CAfile <your CA bundle>
  4. The change. In a clone of the repository, this must list exactly change.files, with the same paths, status letters and blob ids: 
    git diff --raw --full-index --no-renames <base> <head>

Branch HQ's command-line tool does all four: branchhq verify-proof change-proof.json --repo . To make proofs on your own pull requests, see the setup.

Example (shortened)

{
  "format": "branchhq-change-proof/1",
  "change": { "baseRef": "origin/main", "base": "9f2c…", "head": "4b1e…",
              "files": [{ "path": "price.js", "status": "M", "oldBlob": "e69d…", "newBlob": "1a7c…", "added": 4, "removed": 0 }] },
  "commits": [{ "sha": "4b1e…", "author": "Asha <asha@shop.in>", "subject": "Free shipping over 500", "ai": ["Claude"] }],
  "ai": ["Claude"],
  "tests": { "status": "passed", "command": "npm test" },
  "breaks": { "tried": 1, "caught": 0, "notTried": null,
              "missed": [{ "file": "price.js", "line": 6, "before": "if (total > 500) return 0", "after": "if (total <= 500) return 0" }] },
  "findings": { "new": [], "alreadyThere": 0 },
  "verdict": "The project's tests pass on this change. The changed lines were broken on purpose 1 time and the tests caught 0. …"
}

Versions

A new field may be added within version 1; a checker ignores fields it does not know. A change to what an existing field means, or to how the hash is taken, is version 2.

Branch HQ makes Change Proofs on every pull request, with the project's own tests and fixed rules; no AI model judges the change. Questions about the format: hello@branchhq.online.
