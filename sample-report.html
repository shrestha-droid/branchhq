Serious1. Database queries built from user input (SQL injection)

Text a visitor types is pasted straight into a database command, which can let them read or delete data they should not reach.

What to do: Pass every value as a query parameter instead of joining it into the SQL text.

Serious3. Anyone can run any command on the database

The app has a database function that runs whatever SQL it is given, and the website calls it with the public key every visitor has. Anyone can use it to read, change or delete all data.

What to do: Remove the function from the database now. Replace each use with a specific, limited function or a normal query that row-level security protects.

Serious6. Database tables anyone can read (no row-level security)

These Supabase tables are created without row-level security, so anyone with the public key -- which every visitor's browser has -- can read, and often change, every row. (Unless it was switched on later in the Supabase dashboard: worth checking there.)

What to do: Enable row-level security on each table and add policies that let people see only their own rows.

What to do: Add tests for the few flows that matter most (sign-up, checkout, booking) and run them before every release.
