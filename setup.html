Branch HQ on every pull request

Add one file to your repository. Every pull request is then checked against its base branch: only the problems it adds are commented, a new Serious one fails the check, and the change gets a signed, timestamped Change Proof. Problems that were already there never block.

GitHub Actions file GitLab CI file The branchhq command

GitHub

  1. Add the file to your repository and commit it: 
    curl -fsSL --create-dirs -o .github/workflows/branchhq.yml https://branchhq.online/ci/branchhq.yml
  2. Check how your tests install. The tests run on each change, so its dependencies are installed first. The file runs npm ci when there is a package-lock.json; for anything else, change that step to your own install command.
  3. Sign the record and the proofs with your own key (recommended). Once, in your repository, with Node 20+ and the GitHub CLI: 
    curl -fsSLO https://github.com/shrestha-droid/branchhq/releases/latest/download/branchhq.mjs
node branchhq.mjs keygen | gh secret set BRANCHHQ_SIGNING_KEY
    This stores the private key only in the secret and writes the public half to .branchhq/signing-key.pub: commit it. Give the fingerprint it prints to whoever audits your record; anyone who could rewrite the record without your key would have to change it.
  4. Open a pull request. The check comments on it, and the Change Proof and full report are in the run's artifacts.

GitLab

  1. Add the file as branchhq.gitlab-ci.yml and include it from your .gitlab-ci.yml: 
    curl -fsSL -o branchhq.gitlab-ci.yml https://branchhq.online/ci/branchhq.gitlab-ci.yml
    include:
  - local: branchhq.gitlab-ci.yml
  2. Add the variables with the environment scope branchhq-seal, so only the job that signs sees them, not the one that runs the change's code: BRANCHHQ_SIGNING_KEY (from node branchhq.mjs keygen, as above) and, to comment on merge requests, BRANCHHQ_GITLAB_TOKEN (a project access token with the api scope).

What happens on each run

  • On a pull request: the change and its base branch are both checked; only what the change added is reported. The project's tests run on the change, and the changed lines are broken on purpose to see whether the tests notice. A second job, which never runs the change's code, signs the Change Proof and has it timestamped.
  • On a push to the main branch (GitHub): a check is added to .branchhq/evidence.jsonl in your repository, chained to the entries before it, signed and timestamped. A protected branch may refuse that commit; the entry is still in the run's artifacts.
  • Already-known problems: save a report.json from an earlier run as .branchhq/baseline.json and its findings are accepted, never reported.

Checking a proof or the record

node branchhq.mjs verify-proof change-proof.json --repo .
node branchhq.mjs verify .branchhq/evidence.jsonl

Each checks the hashes, the signature against .branchhq/signing-key.pub, and the timestamp; --repo also checks the files the proof names are exactly that change. No Branch HQ server is involved.

What leaves the build machine

  • Your code is read on GitHub's or GitLab's machine, in your own pipeline. It is not sent to Branch HQ or to any AI model.
  • Package names and versions go to osv.dev, to look up known vulnerabilities.
  • Only a hash goes to the timestamp authority (DigiCert).

The personal data report and modernisation plan need a licence key, as the secret BRANCHHQ_LICENCE, used on the main branch only. Questions or help setting it up: hello@branchhq.online.
